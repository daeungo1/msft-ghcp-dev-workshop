## 1. 함정 여섯 개 회고표 (8분)

실습하며 직접 관찰한 내용을 적습니다. 정답이 있는 표가 아니라 내 경험을 남기는 표입니다.

| 단계 | 함정 | 하네스 없이 일어난 일 (내가 본 것) | 붙인 하네스 | 통제 방식 | 붙인 뒤 달라진 점 |
|---|---|---|---|---|---|
| S0 | 문장에 따라 구조와 스타일이 달라짐 | | constitution, 인스트럭션, AGENTS.md | 안내 | |
| S1 | 테스트 없이 완료 보고 | | `tdd` 스킬, 역할 분리 에이전트 | 안내 + 역할 분리 | |
| S2 | 다른 패키지 코드를 직접 import | | import-linter, 훅, CI | 강제 | |
| S3 | 스키마를 추측한 쿼리 | | 읽기 전용 SQLite MCP | 도구 범위 제한 | |
| S4 | 관리자 인가 누락 | | 읽기 전용 리뷰어, rubber duck, CodeQL | 독립 리뷰 | |
| S5 | 하네스가 저장소에 갇힘 | | 팀 플러그인 | 배포·재사용 | |

토론 질문은 세 가지입니다.

* 재현되지 않은 함정이 있었나요? 왜 그랬을까요? 다음에도 안 터진다고 말할 수 있나요?
* 안내와 강제 중, 어느 쪽에서 "끝났다"는 확신이 더 컸나요?
* 여섯 개 중 우리 팀 저장소에서도 실제로 일어나는 것은 무엇인가요?

## 2. 자가진단 (5분)

[templates/self-check-card.md](../templates/self-check-card.md)를 채웁니다.
다섯 축마다 우리 팀에서 가장 자주 새는 곳을 한 줄 적고, 그 자리에 둘 **강제 하나**를 고릅니다.

기준은 다음과 같습니다.

* 한 번 새면 비용이 큰가? 그렇다면 강제입니다 (훅, CI, 리뷰 게이트).
* 어겨도 리뷰에서 잡히는가? 그렇다면 안내로 충분합니다 (인스트럭션, 스킬).

## 3. 공유 (2분)

가장 비싼 병목 하나와 그 자리에 둘 강제를 옆 사람과 서로 읽어 줍니다. 이 한 줄이 워크샵 이후 SDLC 진단과 PoC의 출발점입니다.
